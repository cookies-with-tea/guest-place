## 3. Server: `cargo audit` — одна формально critical находка, реально
      не эксплуатируема в этом приложении

`cargo audit` (после фикса `lettre` в прошлом проходе) всё ещё находит
25 проблем в транзитивных зависимостях — большинство реально глубоко
закопаны (`sqlx`/`redis`/TLS-стек) и требуют крупного апгрейда дерева
зависимостей, не точечного фикса. Одна выделяется severity-меткой:

- [ ] **`zip` crate, severity 9.1 critical** ("ZipArchive::extract()
      применяет Unix-права через симлинки без ограничения цели" —
      classic zip-slip). НО: это **build-dependency** `utoipa-swagger-ui`
      (`cargo tree -i zip` → только `[build-dependencies]`), распаковывает
      только vendored zip с ассетами Swagger UI во время `cargo build`,
      не вызывается на пользовательском вводе ни в одном runtime
      код-пути. Реальный риск в этом приложении низкий несмотря на
      метку — но стоит проверить снова после следующего апдейта
      `utoipa-swagger-ui` (возможно подтянет пофикшенный `zip`
      автоматически), не требует немедленного действия.

## 5. Хардкод вместо `.env`/констант — особенно где значение дублируется

Цель: в коде не должно быть "магических" значений, которые либо меняются
между окружениями (→ `.env`), либо повторяются в нескольких местах (→ одна
именованная константа). Ниже — конкретные находки, не исчерпывающий список
(для "вообще ничего" нужен отдельный построчный проход по каждому модулю).

### Server

- [ ] **`"uploads"` — путь к папке медиа захардкожен буквально в 9 местах**
      (`src/lib.rs`, `src/main.rs` ×2, `src/media/handlers.rs` ×6, плюс
      `ChunkManager::new("uploads")` вызывается заново в каждом из 4
      chunk-хендлеров). Нигде не читается из `.env`, хотя в проде путь к
      volume с загрузками — ровно то, что обычно отличается между
      окружениями. Свести к одному месту (например, `AppConfig` + новая
      переменная `UPLOAD_DIR`, уже есть похожий паттерн для `MEDIA_QUOTA_LIMIT`)
      и прокидывать оттуда везде, где сейчас литерал.
- [ ] **Дефолт пагинации `.unwrap_or(10)` продублирован отдельно в 4
      хендлерах** — `user/handlers.rs:239`, `venues/handlers.rs:414`,
      `i18n/handlers.rs:175`, `media/handlers.rs:355`. Один общий
      `const DEFAULT_PAGE_LIMIT: i64 = 10;` (например, в `core`) вместо
      четырёх копий — иначе при будущем изменении лимита кто-то неизбежно
      поправит не все четыре места.
- [ ] **`src/media/optimizer.rs`: пороги размеров изображений (256, 800,
      1600) — инлайн-числа, каждое используется дважды подряд** (в
      сравнении `if orig_width > 800 ...` и сразу следом в
      `img.thumbnail(800, 800)`) — вынести в именованные константы
      (`THUMBNAIL_MAX_PX`, `MEDIUM_MAX_PX`, `LARGE_MAX_PX`), чтобы не
      редактировать два соседних числа вручную при изменении.
- [ ] Остальное (SQL-литералы, строки статусов и т.п.) по большей части
      — легитимные значения доменной модели, не хардкод в смысле запроса
      — не включал в список намеренно, чтобы не раздувать пункт
      ложными срабатываниями.

### Admin Panel

Централизованные константы (`packages/lib/src/constants/{events,routes,ports}.ts`)
уже существуют — проблема не в их отсутствии, а в том, что несколько
мест их игнорируют и заново объявляют те же строки:

- [ ] **`packages/lib/src/composables/useRealtimeNotifications.ts` и
      `packages/ui/.../UiNotificationBell.vue` заново хардкодят те же 4-6
      строковых имени SSE-событий**, которые уже есть в
      `REALTIME_EVENTS` (`guest_registered`, `media_uploaded`,
      `system_alert`, `content_updated`, `entity_locked`,
      `entity_unlocked`) — как значения TS-union-типа, как имена
      `addEventListener(...)`, как условия в шаблоне (`item.type ===
      'guest_registered'`) и как CSS-классы. Два независимых источника
      истины для одних и тех же имён событий — при переименовании одного
      из них без второго realtime-уведомления тихо перестанут работать.
      Завести на `REALTIME_EVENTS.*` в обоих местах.
- [ ] **Пути внутренней навигации (`router.push(...)`) захардкожены
      россыпью по компонентам**, без общего источника: `/pages`
      встречается 5 раз, `/redirects` — 3, `/menus` — 3, плюс по разу
      `/venues`, `/home`, `/modules`, `/content`, `/docs`, `/login` и
      т.д. в разных файлах `admin-content`/`admin-orchestrator`.
      Централизовать (отдельный `ROUTE_PATHS`-константа рядом с
      `ROUTES`, или вывод путей из самого `ROUTES`, если он всё равно
      переделывается по разделу 1) — иначе при реструктуризации роутов
      придётся искать каждое вхождение вручную.
- [ ] **Если возможно — выносить конфигурационно-контентные вещи в CMS**,
      а не в билд-тайм код: проект уже умеет Schema Builder/CMS для
      контента гостевого сайта — стоит оценить, что из текущего
      "зашитого в код" UI-chrome (подсказки в `mfeHelp.ts`, возможно
      какие-то статические описания/тексты help-виджетов) реалистично
      туда перенести, а что должно остаться частью приложения
      (структура меню, иконки, пути). Не разбирал предметно, какие
      именно места — это отдельное архитектурное решение с владельцем
      продукта, не точечный код-фикс; но раз требование явно
      сформулировано, стоит включить в оценку вместе с разделом 1
      (`ROUTES.ts` и так переделывается).

## 6. Производительность: admin-panel и server должны быть быстрыми

### Admin Panel

Замерено сборкой (`pnpm --filter admin-content build`, реальные цифры,
не оценка на глаз):

- [ ] **Шаренные Module Federation singleton-чанки — главный рычаг**:
      `__federation_shared_element-plus` — **2.2 МБ** (486 КБ gzip),
      `__federation_shared_@admin-panel/ui` — **1.66 МБ** (371 КБ gzip).
      Грузятся ОДИН раз на сессию (шарятся между всеми MFE через Module
      Federation), но именно они определяют время первой загрузки
      админки. 2.2 МБ на Element Plus сильно похоже на то, что библиотека
      подключена целиком, а не точечными импортами — в `packages/lib` уже есть
      зависимость `unplugin-element-plus` (видел в выводе `pnpm install`
      как peer-dependency кого-то ещё), но не проверял, реально ли она
      подключена в vite-конфиг для on-demand импорта компонентов Element
      Plus — если нет, это самый дешёвый большой выигрыш.
- [ ] **`RichTextFullEditor.vue` (Tiptap-редактор) — 1 МБ (237 КБ gzip)
      отдельным чанком** — уже корректно лениво грузится через
      `defineAsyncComponent(() => import(...))` в `UiRichTextField.vue`
      (не блокирует первую загрузку страницы), так что это не баг — но
      раз сам чанк настолько большой, стоит проверить, все ли
      `@tiptap/extension-*` пакеты (их 9) реально используются
      одновременно, или часть можно тоже подгружать по требованию.
- [ ] Остальные бандлы (сами страницы MFE — `VenuesPage` 164 КБ,
      `PageConstructorPage` 130 КБ и т.п.) заметно меньше и не похожи на
      проблему — не включал в приоритет.

### Server

- [ ] **Нет индекса на `guest_user.email`** (`guest_user` — обычный
      `TEXT`, без `UNIQUE`/индекса) — запрос логина (`SELECT * FROM
      guest_user WHERE email = $1`, выполняется на КАЖДЫЙ логин) делает
      полный скан таблицы. Заодно: без `UNIQUE` ничто физически не
      мешает создать двух пользователей с одинаковым email — это не
      только производительность, это ещё и потенциальная проблема
      корректности (`fetch_optional` на дубликате молча вернёт одну из
      двух строк). Нужна отдельная миграция: `UNIQUE INDEX` на email
      (после проверки, что дублей ещё нет).
- [ ] **Нет индекса на `refresh_token.token`/`refresh_token.user_id`**
      — `/auth/refresh` (`WHERE token = $1`) и `/auth/logout/other`
      (`WHERE user_id = $1 AND token != $2`) — оба полный скан, оба на
      горячем пути аутентификации. Таблица к тому же никогда не
      чистится от истёкших токенов (растёт бессрочно) — вместе с
      индексом стоит добавить периодическую чистку `expires_at < NOW()`
      (например, той же фоновой задачей, что уже чистит rate-limiter —
      паттерн `tokio::spawn` + `interval` в коде уже есть, см.
      `auth::handlers::router()`).
- [ ] **N+1-паттерны в bulk-эндпоинтах**: `i18n/handlers.rs:53` (массовое
      сохранение переводов — на каждый элемент отдельный `SELECT`
      "текущее значение для версии") и `media/handlers.rs:1465` (массовая
      ре-оптимизация медиа — на каждый `uuid` отдельный `SELECT` после
      обработки). Оба масштабируются линейно с размером батча от
      пользователя — для большого батча реально заметная задержка.
      Нужно переписать на один запрос с `WHERE x = ANY($1)` вместо цикла.

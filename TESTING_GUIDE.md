# 📖 Архитектура и руководство по автотестированию Guest Place

Данное руководство детально описывает устройство тестовой инфраструктуры монорепозитория **Guest Place**, принципы изоляции, механизмы мокирования, структуру тестовых наборов и регламент запуска.

---

## 🏛️ Общая архитектура тестирования

Монорепозиторий состоит из трёх независимых приложений, каждое из которых использует идиоматичный для своего технологического стека инструментарий:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        Root (Orchestration)                            │
│           Makefile / package.json / Docker Compose                     │
└───────────────┬────────────────────────┬───────────────────────┬───────┘
                │                        │                       │
                ▼                        ▼                       ▼
    ┌──────────────────────┐ ┌──────────────────────┐ ┌───────────────────┐
    │     🦀 Server        │ │   ⚡ Admin Panel     │ │    🌐 Client      │
    │  Rust (Axum, SQLx)   │ │  Vue 3 (Vite + MFE)  │ │      Nuxt 3       │
    ├──────────────────────┤ ├──────────────────────┤ ├───────────────────┤
    │ • Unit (mod tests)   │ │ • Vitest (jsdom)     │ │ • Vitest (happy)  │
    │ • axum-test (API)    │ │ • Component (@vue)   │ │ • @vue/test-utils │
    │ • TestBearer bypass  │ │ • Playwright E2E     │ │ • Nuxt Test Utils │
    │ • PostgreSQL/Redis   │ │ • Turborepo caching  │ │ • FSD Slice tests │
    └──────────────────────┘ └──────────────────────┘ └───────────────────┘
```

## 1. 🦀 Серверный слой (`server/`)

### Стек
- **Тестовый раннер**: встроенный `cargo test`.
- **API Integration**: библиотека `axum-test` для имитации HTTP-запросов без занятия реального системного сетевого сокета.
- **База данных**: PostgreSQL (SQLx pool) и Redis.

### Где расположены тесты:
- **Unit-тесты**: находятся непосредственно в файлах исходного кода в модулях `#[cfg(test)] mod tests { ... }`.
  - Примеры: `src/media/chunk.rs`, `src/media/quota.rs`, `src/pages/model.rs`, `src/menus/model.rs`.
- **Интеграционные тесты**: директория `server/tests/*.rs`.
  - `auth_test.rs`: регистрация, логин, валидация токенов.
  - `features_test.rs`: персистентность feature flags в Postgres.
  - `home_test.rs`: десериализация DTO и сериализация ответов главной страницы.
  - `i18n_test.rs`: CRUD операции словарей переводов.
  - `media_test.rs`: загрузка файлов, валидация квот, поиск.
  - `media_filters_test.rs`: построение сложных SQL-фильтров для медиа.
  - `metadata_test.rs`: оптимизация и очистка метаданных изображений, извлечение палитры.
  - `mfe_test.rs`: генерация манифестов микрофронтендов.
  - `optimizer_test.rs`: генерация WebP и адаптивных вариантов картинок.
  - `venues_test.rs`: парсинг запросов фильтрации заведений.

### Механизм обхода авторизации (TestBearer)
Для интеграционных тестов бэкенда реализован специальный сервисный слой:
Если запрос отправляется с заголовком:
```http
Authorization: TestBearer
```
Сервер пропускает валидацию JWT в БД и подставляет тестового пользователя с полными административными правами (`Role::Admin`).

Этот обход скомпилирован **только** под Cargo-фичей `test-auth`
(`server/Cargo.toml`) — обычный `cargo build`/`cargo build --release`
(и, соответственно, `Dockerfile`) эту фичу не включают, так что бэкдор
физически не попадает в production-бинарник.

### Запуск:
```bash
# Из корня проекта:
make test-server

# Напрямую в директории server/:
cd server && cargo test --features test-auth -- --test-threads=1
```

## 2. ⚡ Админ-панель (`admin-panel/`)

### Стек
- **Раннер**: `Vitest` (с кешированием через Turborepo).
- **Среда выполнения**: `jsdom`.
- **E2E**: `Playwright` (`admin-shell/e2e`).
- **Библиотеки**: `@vue/test-utils`, `@pinia/testing`, `Element Plus`.

### Архитектура тестов:
1. **Shared Packages**:
   - `packages/lib`: тесты хелперов, composables (`useEntityLock`, `useFeatureFlags`, `useRealtimeNotifications`), мапперов данных.
   - `packages/ui`: изолированные тесты дизайн-системы (`UiButton`, `UiInput`).
   - `packages/i18n`: тесты интернационализации, плюрализации и парсинга переводов.
2. **Microfrontend Apps (`apps/*`)**:
   - `admin-shell`: интеграция хост-контейнера, fallback-компоненты при падении ремоутов (`mfeFallback.spec.ts`).
   - `admin-media`: загрузка чанков (`chunkUploader.test.ts`), фильтры, метаданные.
   - `admin-orchestrator`: статус здоровья микрофронтендов (`mfeStatus.spec.ts`).
   - `admin-translations`: редактор переводов (`translationEditor.test.ts`).
   - `admin-users`: страницы управления пользователями.

### Fallback-изоляция микрофронтендов:
В `admin-shell` реализована защита от падения отдельных микрофронтендов. Тест `mfeFallback.spec.ts` проверяет, что при сбое удаленного ремоута отображается заглушка с кнопкой повтора («Повторить подключение»), а приложение не завершается критической ошибкой.

### Запуск:
```bash
# Из корня проекта:
make test-admin

# Напрямую в admin-panel/:
cd admin-panel && pnpm test:unit -- --run

# Запуск E2E тестов:
make test-e2e
```

## 3. 🌐 Клиентский слой (`client/` — Nuxt 3)

### Стек
- **Раннер**: `Vitest`.
- **Интеграция с Nuxt**: `@nuxt/test-utils/config` (`defineVitestConfig`).
- **Среда выполнения**: `happy-dom` для быстрого и легковесного моделирования браузерного DOM.
- **Компонентные тесты**: `@vue/test-utils`.

### Архитектурные соглашения:
Проект следует методологии **Feature-Sliced Design (FSD)**:
- `app/shared/lib/utils/__tests__/*.spec.ts`: юнит-тесты чистых функций (трансформация регистров camel/snake, валидация).
- `app/shared/ui/blocks/__tests__/*.spec.ts`: компонентные тесты CMS-блоков (`VideoBlock`, баннеры, слайдеры).
- `app/entities/**/__tests__/*.spec.ts`: модели данных и бизнес-компоненты сущностей (например, отели, номера, тарифы).

### Особенности мокирования:
- Для компонентов с GSAP-анимациями или специфическими видеоплеерами мокируются внешние вызовы, а тестируется корректность генерации DOM-узлов, расчет аспектов (`aspectRatio`) и правильная трансформация URL видео (YouTube embed, Vimeo player).

### Запуск:
```bash
# Из корня проекта:
make test-client

# Напрямую в client/:
cd client && pnpm test:run
```

## 4. 🔄 Контрактное и сквозное E2E тестирование

### Контрактная синхронизация API
Бэкенд на Rust генерирует спецификацию OpenAPI `server/openapi.json`.
Фронтенд генерирует строгие TypeScript-типы:
```bash
make generate-api
```
Если разработчик изменяет DTO на бэкенде и нарушает контракт, компилятор TypeScript на фронтенде (`pnpm type-check`) сразу выявляет несовместимость до этапа выполнения тестов.

### Сквозной E2E (Cross-Service E2E)
Для полного сквозного тестирования:
1. Docker Compose поднимает сервисы: `db`, `redis`, `server`, `admin-panel`, `client`.
2. Команда `make seed` заполняет базу тестовыми сущностями.
3. Playwright выполняет сценарий:
   - Авторизация администратора в `admin-panel`.
   - Редактирование информации о заведении.
   - Проверка обновленных данных на публичном сайте `client` (`http://localhost:3000`).

## 5. 🎛️ Сводная таблица команд

| Команда | Что запускается | Время выполнения |
| :--- | :--- | :--- |
| `make test` | Все unit- и интеграционные тесты (Server + Admin + Client) | ~15–20 сек |
| `make test-server` | Rust `cargo test` (unit + API integration) | ~5–7 сек |
| `make test-admin` | Vitest по всем микрофронтендам и библиотекам | ~5–8 сек |
| `make test-client` | Vitest по Nuxt 3 компонентам и утилитам | ~2–4 сек |
| `make test-e2e` | Playwright E2E тесты админки в headless Chromium | ~15–30 сек |
| `make test-all` | Полный цикл: unit + integration + e2e | ~40–60 сек |

## 💡 Рекомендации по написанию новых тестов

1. **Для Rust**:
   - Новую бизнес-логику покрывать модульными тестами внутри `src/**/*.rs`.
   - Любой новый эндпоинт в `src/**/handlers.rs` обязательно покрывать интеграционным тестом в `tests/`, используя `axum_test::TestServer` и заголовок `Authorization: TestBearer`.

2. **Для Admin Panel**:
   - Для утилит и сторов — писать тесты в `packages/lib/src/__tests__/`.
   - При добавлении нового микрофронтенда — добавить тест экспортируемых страниц и зарегистрировать в `vitest.workspace.ts`.

3. **Для Client**:
   - При создании нового UI-блока CMS в `app/shared/ui/blocks/` создавать файл `__tests__/BlockName.spec.ts` с проверкой рендеринга дефолтного состояния, пропсов и fallback при невалидных данных.

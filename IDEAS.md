# Guest Place — Идеи и находки (не задачи на сейчас)

В отличие от `IMPROVEMENTS.md` (подтверждённые баги/дыры с доказательствами,
закрываются сразу) — здесь предложения на обсуждение и будущую реализацию.
Ничего отсюда не делать без отдельного решения по каждому пункту.

---

## Функционал

### 1. Silent refresh токена — сессия рвётся каждые ~10 минут простоя

После перехода `access_token` на HttpOnly-cookie (TTL 10 минут) подтвердил:
`authApi.refresh()` нигде не вызывается во всём `admin-panel`. Единственный
`401`-обработчик (`packages/lib/src/api/fetch.ts`) сразу зовёт `clearAuth()`
и уводит на `/login` — ни одной попытки тихо обновить токен через ещё
валидный `refresh_token` (24ч) нет.

Итог: если админ оставил вкладку открытой и вернулся через 11+ минут без
единого запроса за это время — первый же API-вызов разлогинивает его,
хотя по задумке `refresh_token` должен был это предотвращать.

- [ ] Добавить перехват `401` → один тихий `POST /api/v1/auth/refresh` →
      повтор исходного запроса; `clearAuth()`/редирект на `/login` только
      если сам `refresh` тоже упал (`401`/`403`). Нужно подумать над race
      condition при нескольких параллельных 401 одновременно (дедуплицировать
      refresh-запрос, не слать N штук).

### 2. MFA / "Забыли пароль" — заглушки без реализации ни на фронте, ни на сервере

`packages/ui/src/widgets/ui-auth-widget/lib/useAuthWidget.ts` — `AuthMode`
объявляет `'mfa'` и `'forgot-password'`, UI даёт их выбрать, но
`handleSubmit` обрабатывает только `'login'`/`'register'` — переключение в
эти режимы ничего не отправляет на сервер. На сервере нет вообще ни одного
эндпоинта (`grep -rn "mfa\|forgot.?password\|reset.?password" server/src`
— пусто).

- [ ] Решить: реализовать по-настоящему (MFA — TOTP? email-код? Forgot
      password — email со ссылкой сброса, аналогично уже существующему
      email-подтверждению регистрации) — или убрать эти пункты из UI, пока
      не будут готовы. Сейчас это кнопки, которые выглядят рабочими, но
      ничего не делают — хуже, чем их отсутствие.

### 3. Audit/activity log — админские действия нигде не логируются

RBAC теперь реально проверяется (см. `IMPROVEMENTS.md`, закрытые пункты),
но кто именно создал пользователя, изменил права роли, удалил медиафайл,
когда залогинился — нигде не записывается. Версionируются только
`content_entry_versions`/`i18n_translation_versions` (контент и переводы),
остального нет вообще.

- [ ] Спроектировать таблицу `audit_log` (actor_user_id, action, entity_type,
      entity_id, diff/payload, created_at) и минимальный набор точек
      логирования: создание/удаление/смена роли пользователя,
      `update_role_permissions`, удаление медиа, login/logout. Отдельная
      страница в админке для просмотра (поиск, фильтр по пользователю/типу
      действия).

### 4. Permission-matrix UI — страница "Rights" примитивна

`apps/admin-users/src/pages/rights-page/ui/RightsPage.vue` — работает, но:
вкладка на каждую роль, внутри плоский `el-checkbox-group` сырых
permission-id (`mfe:read`, `media:write`, ...) без группировки по модулю,
без человекочитаемых описаний, без сравнения ролей бок о бок, без поиска.

- [ ] Переделать на таблицу-матрицу: строки — permission-коды (сгруппированы
      по модулю: Media / i18n / MFE / User / Access / System / Features),
      столбцы — роли, ячейки — чекбоксы. Плюс понятные подписи (уже есть в
      `permissions.name`/`description` в БД — сейчас не используются в UI).

### 5. Избранное для площадок — фейковая заглушка, фронт её не вызывает

`server/src/venues/handlers.rs:961` — `toggle_favorite` игнорирует `state`,
ничего не пишет в БД, всегда возвращает `is_favorite: true`. Ни в
`admin-panel`, ни в `client` ни одного вызова этого эндпоинта нет вообще.

- [ ] Решить: реализовать по-настоящему (нужна таблица `user_id ↔ venue_id`,
      скорее всего для `client`, не для админки — "избранное" это
      гостевая/публичная фича) — или удалить эндпоинт как мёртвый код.

### 6. Отложенная публикация контента

У `pages`/`content_entries` есть статусы draft/review/published, но
`published_at` — просто метка факта публикации (`pages/handlers.rs:389-392`,
ставится в `Utc::now()` в момент создания/публикации), не таймер на будущее.
Ни одного cron/scheduler-джоба, который переводил бы draft → published по
дате, не нашёл.

- [ ] Добавить `scheduled_at` (nullable) + периодический джоб
      (`tokio::spawn` + `interval`, по аналогии с уже существующими в
      `redirects/handlers.rs`/`monitoring/handlers.rs`), который раз в
      минуту ищет записи с `scheduled_at <= NOW()` и `status = 'scheduled'`,
      переводит в `published`.

## Анализ дизайна / визуала (сначала аудит, реализация отдельным шагом)

Эти пункты — просьба именно проанализировать и предложить находки/варианты,
не реализовывать сразу.

- [ ] **Согласованность визуального языка между MFE admin-panel.** Все ли
      приложения (`admin-content`, `admin-media`, `admin-orchestrator`,
      `admin-profile`, `admin-statistics`, `admin-translations`,
      `admin-users`) реально используют одни и те же design-токены из
      `packages/ui` (цвета, отступы, радиусы, тени), или где-то есть
      локальные захардкоженные значения, которые должны были брать общий
      токен.
- [ ] **Консистентность тёмной/светлой темы.** Пройтись по экранам в обоих
      режимах — нет ли мест с плохим контрастом, "залипшими" цветами из
      одной темы в другой, нечитаемого текста.
- [ ] **Accessibility помимо уже закрытых `aria-label`.** Контраст текста
      (WCAG AA), видимость focus-состояний при навигации с клавиатуры,
      порядок табуляции в сложных формах (schema-builder, page-constructor).
- [ ] **UX конкретных экранов** — отдельным проходом по каждому:
  - Дашборд при входе (`admin-statistics`) — информативность виджетов,
    есть ли то, что админ реально хочет видеть в первую очередь.
  - Rights-страница (см. п.4 выше) — и дизайн, и функционал вместе.
  - Media library — удобство поиска/фильтрации/массовых операций.
  - Page/Schema constructor — насколько очевиден флоу для нового админа.
- [ ] **Адаптивность.** admin-panel выглядит спроектированной under desktop
      — проверить, насколько использование на узких экранах/планшете
      вообще предусмотрено, и стоит ли это менять (не факт, что нужно —
      админка может быть намеренно desktop-only).
- [ ] **Визуальная плотность информации** в таблицах/списках (Users, Media,
      Translations) — не перегружены ли, легко ли найти нужное действие
      среди кнопок.

# Guest Place admin-panel — аудит дизайна/визуала (2026-11-09)

Результат прохода по блоку "Анализ дизайна / визуала" из `IDEAS.md`. Это
находки и предложения, **ничего не реализовано** — решение по каждому пункту
отдельное. Методика: статический разбор кода (grep + чтение компонентов) по
всем 9 приложениям admin-panel + одна живая проверка в браузере (375px
viewport). Расчёт контраста — реальные формулы WCAG 2.1 по токенам из
`packages/ui/assets/styles/core/_tokens.scss`, не на глаз.

## 1. Согласованность визуального языка между MFE

Токен-система (`--gp-*` в `_tokens.scss`, переключение темы через класс
`.dark`, без `prefers-color-scheme`) сама по себе чистая. Проблема —
неравномерное использование: `admin-users`/`admin-profile`/`admin-shell`
почти не имеют захардкоженных цветов в `<style>`, остальные — имеют, и
местами существенно.

Хардкод-хексы внутри `<style>` по приложениям (без `var(--token, #fallback)`,
это легитимный паттерн):

| Приложение | Всего hex | Из них вне `var()`-fallback |
|---|---|---|
| admin-content | 274 | ~160 |
| admin-orchestrator | 52 | — |
| admin-translations | 43 | — (сконцентрировано в 4 файлах) |
| admin-media | 38 | — (почти всё легитимно) |
| admin-statistics | 2 | 0 (реальная проблема — в JS, не в CSS, см. п.2) |
| admin-users / admin-profile / admin-shell | 0–1 | 0 |

**Не всё — нарушение.** Легитимные исключения: `PageSettingsPanel.vue`
(миметика брендовых цветов Google для превью сниппета поиска — `#4285f4`,
`#1a0dab` и т.д.), `*LivePreviewPane.vue` (превью публичного `client`,
у него своя отдельная дизайн-система), `BlockStyleEditor.vue` (фиксированные
свотчи light/dark/accent — так и должно быть).

**Реальное системное нарушение:** `#6366f1` (Tailwind indigo) используется
как замена brand-primary в десятках мест `admin-content`
(`SettingsOnboarding.vue`, `PageListCard.vue`, `TiptapEditor.vue`,
`BlockStyleEditor.vue`, палитры блоков/полей в конструкторе), хотя реальный
токен `var(--gp-primary)` — `#7c3aed` (фиолетовый). Это не edge-case, а
последовательная подмена бренд-цвета на другой на протяжении всего модуля.

**Мёртвые токены:** `--gp-border-color-hover` (определён в обеих темах, 0
потребителей) и `--accent-hover` (используется ровно в одном файле) —
hover-бордеры везде делаются вручную вместо них.

**Отсутствующий семантический токен — корневая причина фрагментации:**
`_tokens.scss` определяет только `--gp-warning`. Нет общего
success/danger/info — каждый файл придумывает свой. Для одного только
"success green" нашлось: `#10b981` (orchestrator, translations), `#42b883`
(бренд-зелёный Vue, orchestrator), `#67c23a`/`#67C23A` (дефолтный зелёный
Element Plus, media, statistics), `#34d399` vs `#4ade80` — **два разных
зелёных в одном и том же admin-content** для одной и той же семантики
("добавлено" в diff) — `VersionDiffViewer.vue` vs `DiffCellContent.vue`. Для
"danger red" — пять разных хексов (`#f04438`, `#ff5f5f`, `#ef4444`,
`#f87171`, `#F56C6C`). Несколько мест пишут
`var(--el-color-success, #10b981)`, как будто Element Plus сам даёт этот
токен — не даёт (EP-тема нигде не импортирована в проекте, см. п.4 ниже про
тот же баг с `el-input`), поэтому `var()` всегда проваливается в тот хекс,
который автор выбрал в моменте.

- [ ] Завести `--gp-success`/`--gp-danger`/`--gp-info` в `_tokens.scss` (по
      аналогии с уже существующим `--gp-warning`) и свести разрозненные
      зелёные/красные к ним хотя бы в новых компонентах.
- [ ] `admin-content`: заменить `#6366f1` на `var(--gp-primary)` в
      перечисленных файлах — чисто механическая замена, зримый эффект.
- [ ] Удалить или начать использовать `--gp-border-color-hover`/
      `--accent-hover`, либо явно решить, что они не нужны.

## 2. Консистентность тёмной/светлой темы

Нашлось 3 воспроизводимых бага — конкретные файлы, конкретная тема, в
которой ломается:

1. **`admin-statistics/src/widgets/traffic-chart/ui/TrafficChart.vue:59,63,78,83`**
   и **`engagement-stats/ui/EngagementStats.vue:62,75,81`** — цвета
   ECharts (`textStyle`/`axisLabel`) захардкожены в JS-конфиге на
   `#94a3b8`/`#fff` — это **значения dark-темы**, ветки для светлой нет.
   В **светлой теме** подписи осей/легенда графика на дашборде (первый
   экран при входе!) рендерятся почти белым по светлому — скорее всего
   нечитаемо. Самый заметный баг из всех найденных.
2. **`admin-translations/.../{TagEditorBody,TagEditorToolbar,TagEditorFooter,TagEditorPreviewPanel}.vue`**
   — вся панель редактора тег-разметки сидит на отдельной
   Tailwind-slate-палитре (`#fff`, `#0f172a`, `#fafafa`, `#e2e8f0`…), **ни
   одного** `.dark`-селектора на все 4 файла. В **тёмной теме** эта панель
   остаётся светлой — светлый остров посреди тёмного экрана.
3. **`admin-media/src/features/media-table/ui/MediaTable.vue:43`** —
   `color: #94a3b8` (это `--gp-text-secondary` тёмной темы) голым
   литералом. Компонент даже подключает `useTheme()`/класс `.is-dark`, но
   нигде его не стилизует (мёртвый код). В **светлой теме** текст заметно
   светлее/выцветшим на фоне соседнего `var(--text-muted)`-текста на той же
   странице.

- [ ] Починить TrafficChart/EngagementStats — самое приоритетное
      (единственный баг, который реально увидит любой админ на первом же
      экране).
- [ ] Перевести TagEditor-панель на `var(--bg-*)`/`var(--text-*)`.
- [ ] `MediaTable.vue:43` → `var(--text-muted)`.

## 3. Accessibility (контраст, focus, tab-order)

### Контраст (WCAG 2.1, реальные коэффициенты по токенам)

| Пара | Светлая | Тёмная | Вердикт |
|---|---|---|---|
| `text-primary` / фон карточки | 15.8–14.8:1 | 16.5–18.0:1 | Проходит с большим запасом |
| `text-muted` / фон карточки | 5.25 / 4.93:1 | 6.74 / 7.34:1 | Проходит AA (≥4.5:1), светлая тема близко к границе |
| `gp-primary` (акцент/ссылки) / фон карточки | 5.70:1 | 6.35:1 | Проходит даже как текст |
| `text-disabled` / фон карточки | 3.04:1 | **2.28:1** | **Не проходит** 3:1 даже для крупного текста/UI-элементов в обеих темах, в тёмной хуже |
| `border-color` (`rgb(255 255 255 / 10%)`/`rgb(0 0 0 / 10%)`) к своему фону | 1.36–1.45:1 | 1.29–1.33:1 | **Не проходит** SC 1.4.11 (нужно 3:1) — это общий токен бордеров карточек/таблиц/инпутов **везде**, границы практически невидимы без `--shadow-sm` |

### Focus-visible — системный баг

`packages/ui/assets/styles/core/_reset.scss:90` (и дублирующий файл
`apps/admin-translations/src/app/assets/styles/_reset.scss:90`) сбрасывает
`outline: none` **на каждый `<button>` в приложении**, без единой
`:focus`/`:focus-visible` замены рядом. Единственное восстановление —
Firefox-only `:-moz-focusring` (строки 138–142). В Chrome/Safari/Edge
клавиатурный пользователь **не видит фокус вообще ни на одной нативной
кнопке**, если конкретный компонент сам не добавил свой индикатор.

Точечно проверенные инпуты (`UiInput.vue`, `FieldConfigPanel.vue`,
`SchemaBuilderHeader.vue`, оба rich-text редактора) — в порядке, outline
убран, но заменён на border/box-shadow. Реальные дыры (убрано и ничем не
заменено):
- `admin-translations/.../TagEditorBody.vue:44` — `.visual-editor`
- `admin-translations/.../TagEditorBody.vue:80` — `.source-textarea`
- `admin-shell/.../GlobalSearch.vue:332` — поле глобального поиска
- `admin-content/.../SplitPreviewPanel.vue:251` — малокритично (косметика fake-browser)

- [ ] Добавить `button:focus-visible { outline: 2px solid var(--gp-primary); outline-offset: 2px; }`
      (или аналог) в `_reset.scss` — один фикс закрывает системный пробел
      сразу везде.
- [ ] Починить 3 реальные дыры точечно.

### Tab-order / доступность с клавиатуры — самая серьёзная находка

Не про порядок табуляции — про полную недостижимость с клавиатуры:

- `admin-content/src/features/page-constructor/ui/PageCanvas.vue:70-82`
- `admin-content/src/features/schema-builder/ui/FieldsCanvas.vue:33-40`

Оба — уже размещённые блоки/поля рендерятся как
`<div draggable="true" @click="...">` без `tabindex`, `role`, `@keydown`.
Добавление новых блоков/полей работает нормально (палитры — настоящие
`<button>`), но **выбрать уже существующий блок/поле с клавиатуры
невозможно вообще** — а именно выбор открывает инспектор-панель настроек.
Переупорядочивание — только нативный HTML5 drag-and-drop, без
`ArrowUp`/`ArrowDown`-альтернативы. Итог: клавиатурный пользователь может
добавлять элементы в конструктор страниц/схем, но не может их
редактировать или переставлять.

- [ ] `tabindex="0"` + `role="button"` + `@keydown.enter/space` на карточки
      блока/поля — закрывает основной сценарий (выбор).
      Клавиатурный reorder (кнопки/горячие клавиши вверх-вниз) — отдельная,
      более объёмная задача.

## 4. UX конкретных экранов

### Дашборд (admin-statistics)

Единственный роут `/` (`pages/AnalyticsPage.vue`): сводка KPI, график
трафика, engagement, retention-когорты, воронка конверсии, источники
переходов, селектор периода 7/30/90 дней, кнопки "Обновить"/"Экспорт". Это
**чисто маркетинговая аналитика публичного сайта** — посетители, сессии,
клики, воронки. Ноль операционного CMS-контента.

**Пробел:** ни audit log, ни отложенная публикация (обе фичи — из этой же
сессии) нигде не видны на первом экране. Новый админ, зайдя в систему, не
может увидеть "что изменилось недавно" или "что скоро опубликуется
автоматически" — оба вопроса решаются одним запросом
(`GET /api/v1/audit`, фильтр `status='scheduled'` по pages/content_entries),
но дашборд ничего из этого не показывает. Естественный первый вопрос
админа CMS — "что требует внимания прямо сейчас" — дашборд не отвечает
вообще, отвечает только "как дела у публичного сайта".

Мелочь: `refreshData()` (`AnalyticsPage.vue:54-57`) — это
`window.location.reload()`, а не реальный рефетч, при выделенной кнопке
"Обновить" выглядит небрежно.

### Media library (admin-media)

Неожиданно хорошо сделано — лучше, чем предполагал исходный пункт
IDEAS.md. Фильтры (поиск, папка, тип, категория, теги, пресеты размера,
диапазон дат) все на месте, поиск матчит не только имя файла, но и
title/alt/категорию/теги. Bulk-операции (`useMediaTableBulkActions.ts`) —
перенос в папку, удаление, массовое добавление тегов, смена категории,
конвертация в WebP — все три bulk-роута сервера
(`PATCH /bulk`, `POST /optimize/bulk`, `POST /batch/move`) реально
прокинуты в UI, ни одной "осиротевшей" серверной возможности без
интерфейса. Папки, мультизагрузка с drag-and-drop — всё на месте.

Мелкие пробелы: нет фильтра "неиспользуемые/осиротевшие" медиа; диапазон
размера в байтах есть в данных (`minSizeBytes`/`maxSizeBytes`), но в UI —
только пресеты (small/medium/large/huge), без произвольного диапазона.

### Page/Schema constructor (admin-content)

В целом сделано хорошо: `BlockPalette.vue`/`FieldTypePalette.vue` — имя +
иконка + описание + поиск, живое превью страницы есть
(`LivePreviewPanel.vue`), `FieldConfigPanel.vue` — инлайн-валидация, нет
сырого JSON нигде. Два конкретных узких места:

1. **Relation-поле настраивается вслепую.** `FieldConfigPanel.vue:72-77` —
   "Relation To (Schema slug)" это обычный текстовый `<input>`, куда админ
   должен **вписать точный slug по памяти**; список существующих схем уже
   загружается в этом же фиче (`useSchemaList.ts`), но сюда не прокинут —
   ни dropdown, ни autocomplete.
2. **Пресеты блоков хранятся только в localStorage и падают тихо.**
   `useBlockPresets.ts:35-50` — "Сохранить как пресет" пишет в
   `localStorage`, ошибки глотаются `console.warn` без `ElMessage`. В
   приватном окне или с отключённым storage админ видит успешное закрытие
   диалога, а пресет просто не сохраняется; пресеты вдобавок никогда не
   синхронизируются между машинами/коллегами — нет серверной таблицы.

Архитектурная заметка (пересекается с п.1): обе палитры используют
хардкод-indigo для hover/active вместо `var(--gp-primary)` — тот же
off-brand цвет, что и остальной admin-content, заметно внутри одного и
того же флоу (бордер кнопки "добавить" — токен-фиолетовый, а hover-заливка
— индиго).

### Rights-страница

Матрица ролей/прав уже реализована в этой сессии — реализация и дизайн
сделаны вместе, отдельного прохода не требуется.

- [ ] Дашборд: добавить виджет "последние действия" (из audit_log) и/или
      "скоро опубликуется" (из scheduled-контента) — закрывает реальный
      операционный пробел, а не косметику.
- [ ] Relation-поле в schema-builder: заменить текстовый инпут на
      `el-select` со списком существующих схем.
- [ ] Пресеты блоков: либо явный `ElMessage.error` при сбое записи в
      localStorage, либо (лучше) перенести на сервер.

## 5. Адаптивность

Admin-panel спроектирована исключительно under desktop — гипотеза
IDEAS.md подтвердилась с запасом. По всему монорепо (9 приложений,
`apps/` + `packages/ui`) ровно **6 файлов** вообще используют `@media`, и
каждый — на свой, несогласованный брейкпоинт (`900px`, `840px`, `840px`,
`1200px`, `768px`, `1024px`). При этом в `packages/ui/assets/styles/_variables.scss`
есть готовая карта `$breakpoints: (desk: 1920, tab: 1440, mobi: 568)` —
ни один из 6 файлов её не использует, карта фактически мёртвая.

Сам каркас (`UiSidebar.vue`) — ручной toggle collapse (64px/240px) без
единого `@media`: сайдбар никогда не схлопывается и не прячется
автоматически на узких экранах, всегда занимает минимум 64px.

Живая проверка (375×812, `admin-users`, страница "Пользователи"):
сайдбар фиксированной ширины съедает большую часть экрана, список
пользователей обрезан до нечитаемой полоски, появляется горизонтальный
скролл. Не теоретическая, а воспроизводимая поломка.

- [ ] Решение — не "предполагать нужно", а явно выбрать: либо
      admin-panel намеренно desktop-only (тогда стоит хотя бы показать
      `"Откройте с экрана шире 1024px"` вместо сломанного layout на
      мобильном), либо делать реальную адаптивность (тогда начать с
      `UiSidebar` — auto-hide/overlay-режим на `$breakpoints.tab` и ниже
      — это единственный компонент, который ломает КАЖДЫЙ экран сразу).

## 6. Визуальная плотность информации (Users / Media / Translations)

Рейтинг от худшего к лучшему:

**1. Media (`MediaTableColumns.vue`) — худший случай.** 11 колонок
считая чекбокс: имя, тип (тег), категория, теги (несколько чипов), папка
(цветная точка + бейдж), превью (миниатюра + точка доминирующего цвета),
размер, источник (тег), дата, действия. Каждая строка одновременно
держит миниатюру, до 3 тег/бейдж-элементов и цветовую точку. Хуже того —
фильтры по категории/тегам сами по себе заглушки:
`MediaTableColumns.vue:76` (комментарий "These would ideally come from a
separate API", захардкожены только `Marketing/UI-UX/Content`) и `:111`
(фильтр по тегам — вообще без `<el-option>`, чистый free-text). Фильтры
есть, но реально помочь найти что фильтровать — не могут.

**2. Translations (`TranslationsTable.vue`) — неравномерно.** Всего 4
колонки данных (ID, Namespace, Key, Translation) — меньше всех трёх, но
**4 icon-only кнопки действия на строку** (Edit, History, "Где
используется", Delete) в колонке на 200px — больше, чем у Users или Media,
при наименьшем числе данных-колонок. `id` первой 120px-колонкой — тоже
слабый выбор для "окинуть взглядом" вместо Namespace/Key.

**3. Users (`UsersTable.vue`) — лучший баланс.** 7 колонок, но Role и
Status редактируются инлайн (`el-select`/`el-switch` прямо в ячейке), а не
отдельными кнопками — колонка действий остаётся Edit + Delete.

**Системный паттерн:** `el-dropdown` (overflow-меню) уже есть в кодовой
базе и используется — но только для *bulk*-действий над мультивыбором
(`MediaBulkActionsBar.vue`). Ни одна таблица нигде не сворачивает
*построчные* действия в overflow — каждая строка всегда рендерит каждую
кнопку целиком, сколько бы их ни было. Translations (4 кнопки/строка) —
самый очевидный кандидат на этот уже существующий паттерн.

- [ ] Translations: заменить 4 icon-only кнопки на `el-dropdown` (Edit —
      основное действие остаётся отдельной кнопкой, остальные три — в
      меню).
- [ ] Media: либо реально завести API для категорий/тегов (данные явно
      есть — теги показываются в самих строках), либо убрать заглушки
      фильтров, пока они не работают по-настоящему.

## Сводка по приоритету

Если выбирать, с чего начать (не просили реализовывать, но если решите):

1. **TrafficChart/EngagementStats светлая тема** (п.2) — баг на первом
   экране, который увидит каждый админ.
2. **`button:focus-visible` в `_reset.scss`** (п.3) — один фикс закрывает
   системный пробел клавиатурной доступности сразу everywhere.
3. **Keyboard-доступность page-constructor/schema-builder canvas** (п.3)
   — сейчас блокирует флоу полностью для клавиатурных пользователей.
4. Дашборд: виджет из audit_log/scheduled (п.4) — реальный операционный
   пробел, а не косметика.
5. Остальное — дизайн-гигиена (п.1, п.6), важно, но не блокирует.
